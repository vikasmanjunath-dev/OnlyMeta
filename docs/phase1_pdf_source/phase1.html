The solution in one sentence

A local collector keeps raw logs and secrets inside the customer environment and sends only allow-listed metadata to a multi-tenant SaaS, which shows four health states, explainable anomalies and incidents, and proves what left the building with an Egress Proof Panel.

Problem

Raw logs shipped to a central platform expose secrets, create blind spots and drown operators in noisy alerts.

Solution

Two tiers: collect, redact and analyse locally; transmit metadata; correlate and explain centrally.

Proof

Egress panel, sent = received IDs, timestamps for every latency target, tenant isolation test.

CRITERION 1

Why raw telemetry stays local, and SaaS gets metadata only

Problem understanding: the risk, the principle and why metadata is still enough

Data exposure risk

Shipping raw logs, payloads and credentials to a central platform widens the attack surface and can breach compliance obligations.

Operational blind spots

Teams running many sites, networks and apps need one consolidated view without losing local control of their data.

Alert fatigue

Static thresholds create noisy, duplicated alerts. Operators need correlated incidents with likely causes.

Global operations

Customers span regions, time zones and data-residency rules, so the platform must be designed for that from day one.

Representational model: detail shrinks as data moves right; decisions are taken locally, so only a thin metadata layer crosses the boundary.

Why the SaaS still works with metadata only

  • Anomaly detection needs numbers over time (rolling baseline per metric), not log text.
  • Correlation needs which node, when and how severe: pseudonymous node IDs plus a dependency map are enough.
  • Security signals are summarised locally (failed logins per 60 s) so the SaaS sees a risk indicator, never the credentials.
  • Recommendations are explained from metric deviations, so no payload content is required.

Three guarantees we can demonstrate

  • Structural allow-list: a field not in the schema cannot be serialised.
  • Visible proof: Egress Proof Panel shows the exact payload before it leaves.
  • Safe delivery: persist before send, delete only after ACK; unique payload_id means no duplicates.

Before observability vs. what we now observe

The situation before monitoring, and what the two-tier solution makes visible
Q1

BEFORE observability: what was the situation?

  • Blind spots: sites, networks and apps watched through separate tools; failures were often noticed when users complained.
  • Data exposure: the usual fix shipped raw logs and payloads to a central platform, moving credentials outside the customer's control.
  • Alert fatigue: static thresholds gave duplicate, noisy alerts; one database bottleneck looked like many unrelated problems.
  • Security signals buried: repeated failed logins found only by reading raw logs after the fact.
  • Silent failures: a dead agent kept showing its last good value, so nobody knew it had stopped.
  • No proof: nobody could show exactly what data left the environment.

CRITERION 4 · EVIDENCE

What stays local, what is redacted, what is sent

The allow-list, with a before-and-after example and the three-layer defence

STAYS LOCAL · never serialised

  • Raw log lines and payload bodies
  • Passwords, API keys, tokens
  • Usernames and email addresses
  • Raw IP addresses and real hostnames
  • Any free-text field
  • Anything not defined in the schema

Raw store retention: 1 hour, then deleted.

REDACTED / TRANSFORMED

  • Secret patterns (sk-…, password=, tokens) scrubbed
  • Hostnames and source IPs → HMAC pseudonyms: n- + HMAC-SHA256(tenant key, value)[:10]
  • Failed-login events → a count per 60 s
  • Free text → dropped
  • Payload still matching a secret pattern → BLOCKED, logged

SENT · allow-listed fields only

  • payload_id, tenant_id, collector_id, region
  • collector_version, config_status
  • event_time (UTC), source_tz, sent_at, is_replay
  • node_pseudonym, event_category, severity
  • metrics: cpu, mem, disk, bandwidth_mbps, latency_ms, packet_loss
  • auth_failures_60s, auth_source_pseudonym

Metadata-only SaaS flow: how isolation is enforced

  • Per-collector API key bound to one tenant and one region; tenant_id is taken from the key, never from the request body.
  • tenant_id on every row and in every query; SSE streams are scoped per tenant.
  • Region store per tenant: one SQLite file per region; a payload whose region differs from the tenant's is rejected.
  • Isolation test: beta token sees zero alpha rows.
  • Production path: separate schemas or stores per tenant, mTLS, key rotation.

CRITERION 5 · TELEMETRY + GLOBAL

Simulated-telemetry plan and early global awareness

How we get comparable data without real devices, and how the design respects regions, time zones and residency

Simulated-telemetry plan

  • The organizer stream is the source of truth: the same stream for all teams, so bursts, latency spikes and outages are injected identically.
  • If its format differs from our sample, only adapter.py changes.
  • Until the spec arrives, sample_stream.jsonl (60 lines incl. fake secrets) unblocks P2–P4 by hour 1.5.

Early global-readiness: regions, time zones, residency

  • Regional ingest: each tenant sends to its assigned region.
  • Residency: metadata stays in the tenant's region (simulated with one DB file per region).
  • UTC + source timezone on every event; ordering by event time, not arrival.

Regions

alpha → IN, beta → EU, configured in tenants.yaml.

Time zones

UTC for logic, source timezone for display; charts labelled UTC.

Out-of-order

Late events slot into place by event time without corrupting trends.

Idempotent retry

payload_id is created once; retries after outages never duplicate.

JUDGE Q&A · EVIDENCE

Phase 1 judge questions, evidence pack and self-check

Short, precise answers: say exactly what leaves, pick few use cases, show a believable plan

Exactly what leaves the environment?

Only schema fields: numeric metrics, UTC time + source timezone, HMAC-pseudonymous node and source IDs, severity, category, counts (failed logins per 60 s), version, config status, payload_id. Raw logs, secrets, usernames, raw IPs, hostnames and free text stay in Tier 1.

Why is metadata enough for AIOps?

Baselines and z-scores need numbers over time; correlation needs which node, when and how severe (pseudonyms plus a dependency map); recommendations are explained from metric deviations, not log text.

How do you stop a secret slipping out?

Three layers: schema allow-list (structural), regex scrub, and an outbound scanner that blocks a matching payload and logs it as BLOCKED. The Egress Proof Panel shows the result live.

Who can see what?

Raw data: the customer on the Tier 1 UI only. Metadata: that tenant's operators only, enforced by key-bound tenant_id on every query. Other tenants and SaaS staff get nothing raw, because it never arrives.

Is the scope realistic in 24 hours?

P0 is small and proves the boundary. Checkpoints at hours 5 and 8, freeze at 13, a written cut list, and hours 15–24 as buffer.

How do you test without real devices?

The organizer stream plus our injector for the eight judge scenarios. Honest limit: no real SNMP or syslog at volume; scale path is stated.
